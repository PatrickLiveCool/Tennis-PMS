## 1. 用户已确认的范围

本任务来源为 2026-09-14 用户对“房型与价格”页面建议的两条批注。

- 不限于调整现有价格：支持新增和删减房型、给实际房间分配房型、调整床位结构。
- 针对该类房型统一调价，保留现有 1、7、14、30 晚基准总价，不需要节假日或每日定价。
- 入口为“设置 → 房型与价格”。展示销售单位、关联房间、现行价格；支持生效日期、发布前试算、历史版本、操作人和修改记录。
- 用户本轮未授权执行生产库存变更、生产价格发布或部署；本功能中的“发布价格”是未来产品操作，不等于本次已获生产发布授权。

本稿定义开发边界；D1-D3 已有用户明确确认，其他未决经营场景不自动扩展。

## 2. 已确认的业务决定

2026-09-14 用户已逐项选择以下规则，直接据此实施，不重复请求批准开发。

| 编号 | 已确认规则 | 具体影响 |
|---|---|---|
| D1 | 删除、停用以及有订单时的结构调整 | 未投入使用的误建房型允许删除；已使用的房型、房间或床位停用并保留历史。存在在住、未来预订或有效占用时，先通过既有业务操作处理，再调整。本次不直接迁移未来预订。 |
| D2 | 新价格的生效口径 | 按新订单的入住日选择价格；例如提前发布 10 月 1 日价格，9 月新建的 10 月入住预订使用新价。已建订单仍锁原版本。不按开单日选价。 |
| D3 | 修改权限 | 仅管理员可维护房型、房间床位及统一价格。后端和数据库命令边界均须验证。 |

关联会员问题：停用房型或减少最后一间适用房源时，必须识别已售未到期会员权益，列出影响，不得自动转换权益或删掉合同。若实际维护场景要求取消全部适用库存，需要补充权益安置规则；不由当前维护命令代替经营决定。

## 4. 页面与操作

### 4.1 房型列表与详情

- 显示名称、卫浴类型、销售模式、默认床位结构和可住人数、关联房间数、有效床位数、启用状态及现行价格。
- 支持新增、编辑、删减以及查看历史；删除和停用用准确文案区分，资格与行为按 D1。
- 列表可切换查看停用项；详情保留关联房间与历史变更入口。
- 房型名称可由经营人员填写，内部稳定标识由系统生成，不要求工作人员维护产品 code。

### 4.2 房间与床位

- 在房型详情查看实际房间，按楼栋及房号定位；支持分配或重新分配房型，并调整对应物理床和可拆售床位。
- 每次提交前展示原房型、目标房型、床位增减及调整后的容量、受影响的订单或占用。
- 区分“物理床”与“可单卖床位”：仅整房销售的标间有两张实体床，不自动生成两个可单卖库存。
- 多人间整间销售仍占用全部有效子床；一床已占时整间不可售，整间已占时任何子床不可再售。
- 整房与床位销售模式切换属于库存结构变更，使用与增减床位相同的事务、占用检查和历史保护。
- 删除或停用的历史身份不能复用给另一实体。历史查询不因 active 过滤而缺失房间或床位。

### 4.3 房型价格

- 编辑该房型的 1／7／14／30 晚基准总价，明确单位是“元／床位”或“元／整房”的对应档位总价。
- 延续已确认时长分档、跨月连续计算和最终总额一次整元舍入规则。
- 多人间整租延续现有“床位锚点 × 物理床数”规则，展示派生整间价格；本次统一调价不引入独立整租折扣规则。
- 选择生效日期、填写修改原因；同时展示旧价、新价及价差。
- 发布前输入入住、退房日期和销售单位，使用正式计价引擎试算，展示住宿晚数、选用档位和最终金额。试算不能创建真实订单或占用库存。
- 编辑表单与待确认预览作为草稿；价格历史区分已发布、待生效及同日更正版本；发布后的数字不可覆盖修改，更正须新增版本。
- 发布按物业完整、可复算的价格快照生成新版本；只修改一个房型时，其他房型价格保持对应有效值。未来已有待生效变更时，不能用过期快照覆盖另一房型的已排期价格。
- 页面展示的“现行价”和“所选日期适用价”要有明确日期口径；不能把未来发布的价格直接标成今天现行价。

## 5. 历史、事务与授权约束

### 5.1 目录与价格版本

- 将物理资产稳定身份与可变销售配置分开；订单或住宿分段须能解析成交时的目录配置和价格产品，历史不跟随当前房型被重新解释。
- 实施前确定历史快照落点、旧数据回填和所有读取路径。不能只给房型表加版本号却仍用当前库存行复算历史。
- 现有订单的续住、改期、缩短、换房使用原锁定政策，不自动涨价。原政策不含新房型时，不得悄悄退回当前新政策；预览须明确说明缺少原政策价格。若用户要求这种换房，需要另行明确计价规则。
- 既有会员产品价格、适用房型和权益合同沿用现有规则；本次修改住宿房型价格不自动修改会员卡售价或已售权益。
- 报价、确认与发布并发时，确认校验预览所基于的版本；过期预览需要刷新，不能提交页面没展示的价或结构。

### 5.2 写入流程

- 复用项目命令 Preview → Confirm → Receipt 和结果查询恢复机制。
- 房型变更、库存投影、价格引用和审计在同一事务内完成；任何失败全部回滚。
- 目录修改与开单、换房、维修占用等写入采用一致的锁协议；确认时重新验证整个受影响房间及子床，不只检查被删床位。
- 检查覆盖在住、未来预订、维修、内部占用、HELD 会员覆盖以及当日应退未退的实际占用。具体能否迁移未来预订以 D1 为准。
- 使用版本校验防止两人覆盖修改，幂等键防止重复创建房型、床位或政策版本；超时先查询原操作结果再决定重试。
- 记录操作者、物业、时间、原因、前后内容、命令 ID 和引用版本；失败或拒绝不能留下半份目录或已发布政策。

### 5.3 权限与运行身份

- 按 D3 授予独立维护能力，页面入口、读取接口和写命令分别落实授权，不根据页面隐藏代替后端校验。
- 跨物业访问或写入拒绝；普通员工和外部 Token 不能通过手工指定旧政策或库存 ID 绕过新规则。
- 不授予应用任意 SQL 或放宽整个库存表的身份修改权限。新增受控写入与既有 `qintopia_runtime` 受限运行身份相容。
- 发布、停用、床位调整结果不明时展示原命令恢复入口，避免用户重复提交。

| 命令失败、超时重试或权限被撤销 | 原子回滚或返回原结果，不重复新增，确认时权限失效不能完成修改。 |

## 9. 最终实现与工程约束

- room_catalog_state 保存运营快照及版本；room_catalog_links 保存实体房间与历次库存身份；room_catalog_heads 解析入住日期对应价格；room_catalog_changes 保存不可变操作历史。
- 每次结构调整停用原房间及全部子床，追加新的库存身份，保留原订单引用。床数允许 1–100，按床销售容量等于床数；物理床与独立可售床位仍分开。
- 误建且无房间、价格或会员关联的房型可删除。已使用房型销售模式不能直接改写；先新增目标模式房型，再给无占用房间重新分配。停用房型会停用其所有启用房间；恢复房型后按需单独启用房间。
- 发布四档价格按元输入、分存储，每个档位大于 0 且不超过 20 万元；不能追溯发布到过去日期。每次发布重建各生效日的完整政策快照，保证其他房型已排期价格不丢失。
- MANAGE_ROOM_CATALOG 仅由有效管理员网页登录会话执行。共享/独占物业目录锁协调报价、预览、确认、库存占用；数据库受控函数重检版本、会话、占用、实体身份和完整子床，延迟约束要求回执与审计一起提交。
- API 使用 action 判别的互斥输入结构，避免多分支校验误删另一个操作的字段；客户端复用已有命令恢复机制。
- 061 迁移须与新版应用一起发布；deploy/release-policy.json 标记 forward-only，不能仅回退旧镜像。
