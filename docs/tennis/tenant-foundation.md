# F1：租户、场馆与受控库存

依据当前 MVP：平台 → Tenant → Venue → Court；校区与场馆同层。该切片补齐资产归属与内部员工权限，不表示登录、客户支付或完整多租户后台已完成。

## 契约

- 租户、场馆、球场均有稳定 ID。场馆和球场名称可在不同租户重复；禁止跨租户引用场馆或球场。
- 主体与租户会员资格分开。管理员可管理本租户；普通工作人员须有显式动作权限及授权场馆；只读人员只有查询权限。
- 所有内部库存函数必须接收由上层认证服务取得的 `subjectId + tenantId`，不得将浏览器直接提交的身份视为认证结果。现有无主体函数签名关闭；公开认证/API 待后续切片。
- 每次查询、创建、改期和释放重新核对租户服务状态、员工资格及场馆范围。写操作在同一事务中锁定授权记录并写审计，权限调整不绕过在途事务。
- 改期同时检查原场馆和目标场馆权限；取消/改期失败保留原占用。读、改、释放均用租户条件，未知或无权资源不返回其他租户的业务资料。
- 球场与占用均持有 tenant_id，通过复合外键保证归属；数据库管理员仍是受信任运维边界，本切片不声称超级用户受 RLS 隔离。
- 空间授权与价格配置分离。基础权限包含 read、book、manage_assets、manage_prices、refund、hold_unpaid、manage_members；其实际业务命令按后续切片落实。
- 追加迁移，不改 001/002 checksum；如果旧 courts 已有无租户数据则拒绝升级，要求显式归属映射，不自动创建真实租户或把旧资源塞到任意租户。本地开发库已只读核对无旧资源。

## 最低验证

两个合成租户、同名球场可正常独立占用；查询/改期/释放不能跨租户；同租户未授权场馆拒绝；只读人员不能写；停用租户或撤销成员立即拒绝后续调用；直接 SQL 不能跨租户引用场馆/球场；改期冲突保原预约与版本；审计与业务同事务。原 15 分钟和并发防重测试继续通过。

测试只清理本次合成主体、租户及记录；不清空数据库或住房数据。自动验证后再记录结果，运营 UI/登录/客户自助人工验收后续单独完成。
