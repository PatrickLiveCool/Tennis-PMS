# 储值和混合付款实施契约

状态：2026-09-19，线下充值/赠送、余额/混合付款、取消/到期释放及订单退款已完成内部服务和自动验证；模拟线上充值见 `online-topups.md`。真实支付/退款渠道发起器、异常待办处理与 UI/API 尚未完成。继承 `booking-transactions.md`，不改变用户集中确认的规则。

## 不变量

- 金额均为人民币分，整数运算。账户按 tenant/customer 唯一；同租户跨场馆可用。任何入账来自有凭据的充值或原路退款，不能直接设定余额。
- 充值本金、赠送、可用和预留分别存储。每批按到账先后使用，分摊按该批本金/赠送比例取整，尾差不超过该构成实际剩余额度。本金与赠送合计严格守恒。
- 请求同时使用余额和微信时，先原子预留指定余额，只向支付渠道申请差额。订单全部应付金额满足后才确认预订。余额不足拒绝，不透支、不静默改为其他付款方式。
- 同一订单同时只有一笔待处理付款。MVP 先用租户级事务锁串行化订单/资金命令，随后按授权 → 场馆 → 订单 → 支付记录 → 钱包取锁；钱包另有账户行锁。这样跨场馆批量到期及付款不会反向锁住不同客户账户；不同租户仍可并行。高吞吐优化后置，不能先移除互斥再补并发验证。
- 纯余额付款在一个数据库事务完成预留、消费、付款状态和订单确认。混合付款到账后同事务转消费；失败、取消或到期只释放未消费预留。
- 付款、订单、钱包流水及幂等回执关联同一业务命令；超时未知结果可查回执，不换键重扣。旧的未付款取消/到期路径必须调用资金释放，不得留下冻结余额。
- 回调必须验证签名以及商户、币种、金额、订单关联；重复事件不重复消费。同一渠道交易号不能支付两单。订单过期或取消后迟到的实收进入明确退款待办，不能抢回库存或重新消费已释放的余额。
- 授权员工可凭真实收款凭据登记线下充值，记录办理主体、场馆、原因、本金和赠送；同凭据不能重复充值。客户仅能使用可信身份绑定的余额；手机号查询不产生扣款权限。

## 外部条件与验证

当前无商户号、服务器和域名。本地支付适配显式标记 MOCK，只接受本地模拟服务签名事件；不提供能伪造生产到账的匿名入口。真实渠道实现与商户验证后置为外部待联调工作，不计为已通过。

验证覆盖跨租户、跨校区、批次顺序、本金/赠送取整、并发不透支、全余额和混合支付、重复回调、错误金额/商户、超时释放、付款与到期竞争、迟到实收待办和可追溯账目。订单退款还必须按原批次及原付款来源恢复，详见总交易契约；本切片不能用增加新充值批次代替退款。

## 按明细退费

- 员工以当前订单版本，明确每条明细的退款金额及是否取消使用；理由必填。客户/外部智能体无权自行定退款金额。可以取消部分明细，其余占用保留；费用由人工按业务判断确认，含零元退款。
- 已申请且未完成/失败待重试的退款仍占用可退额度。检查明细金额及原支付来源累计额度，防止并发申请/改键重试超退。原操作键重试返回当前退款状态。
- 退款按原订单剩余可退来源比例分到分，最后尾差严格守恒；钱包回到原批次本金/赠送。纯余额立即完成；外部部分确认前，钱包退款也保持待处理，界面必须区分场地已取消与退款未完成。
- 外部成功事件需要原商户、原付款交易号、退款 ID、币种和外部退款金额全部匹配。失败可重试同一退款 ID，已成功后迟到的失败不回滚；重复成功不重复增加余额。当前模拟只验证结果接收，真实退款发起/查单仍待接入。
