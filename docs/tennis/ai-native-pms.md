# 当前开发决定：AI Native PMS

日期：2026-09-20。用户最新确认优先于此前讨论稿。本文是开发依据，具体实现和验证另行记录。

## 产品目标

第一步让场馆愿意用、用得起 PMS：以低位 SaaS 服务费、试用转付费切入，减少场地经营的 IT 和管理成本。先服务使用本 PMS 的场馆。费率、试用期限和收费自动化可后续决定，不阻塞当前产品。

客户和员工通过智能体 Gateway 进入交易流程。外部 Runtime 调用 PMS 的查询、报价、占位、付款查询与预订接口；PMS 控制真实库存、确定性计价、订单、资金、授权与审计。标准链路不包含电话接单。规模扩大时不以同比增加逐单操作人员为前提；明确证据下自动办理，归属不明、到账异常、授权退改等例外由人工处理。

## 两类 AI 入口

| 入口 | 配置与职责 |
| --- | --- |
| PMS 后台 AI 助手 | 保留 GreenPMS 的入口和使用习惯；平台运营管理员在 UI 设置模型名称、Base URL、API Key、启停及测试连接。租户使用但无配置/密钥权限。首期只读查询、解释及业务入口引导。 |
| 外部业务智能体 | Runtime 独立运行，一端连接客户/员工 Gateway，另一端调用 PMS 受控业务 API。模型及运行参数在 Runtime 自身管理。PMS 不开发该 Runtime，不把它的部署作为本地 PMS 验收门禁。 |

后台私有助手会话与外部业务会话分离。客户与员工外部会话的身份绑定、消息去重、幂等命令、接管和权限撤销继续保留。模型回复不能替代库存、到账或退款事实。

## 支付与自动化

用户认可分阶段路径：当前企微收款并在 PMS 对照；少量平台订单先记录订单和实收归属；规模化时再接入合适的支付产品及分账结算。

本地用明确标识的合成流水验证业务。可信流水带有确定的业务支付引用且租户、商户、金额、币种核验通过时，可以自动对应原订单或充值。只有金额相同、昵称相似、聊天宣称付款或截图，均不能自动认定支付成功。不明归属交给授权员工核对；关联流水与记录资金必须同事务防重，不能把同笔实收同时用于订单与充值。

付款晚于占位期限时，记录实收并进入异常处理，不重新抢占库存；余额预留、禁止透支、本金/赠送比例和原路退款规则不变。人工退款金额及理由仍须由授权人员确认。

一位预订人可办理同场馆多片、不同时间的组合预约，允许余额加外部补差；多人付款份额、约球匹配产品、佣金与分账结算后置。它们的商业规则不再作为当前 PMS 开发门禁。

## 远期边界

PMS 是整体网球平台的经营与交易组件。平台将来汇聚已合作场馆供给，应通过明确作用域、可审计的服务接口及库存事件实现；不设置跨租户万能密钥或不可撤销的隐藏权限。库存查询/成交权限与租户经营资料权限分开，不能因平台需要供给目录而放宽现有租户隔离。

当前保留订单、支付、实收、退款及后续平台费用的独立事实边界，不提前产生佣金或结算义务。准确库存、自动执行与异常可定位，是当前开发即需落实的质量目标。

## 当前执行范围

继续现有 demo 开发，补齐后台助手直连模型及多租户收款对照，保留 GreenPMS 视觉和便捷操作。完成适当自动验证后交付本地人工验收。真实企微账单/商户联调、真实模型连接、外部 Runtime、真实资料导入与生产部署分别记录，未发生就不宣称完成。

部署拟沿用 GreenPMS 服务器，待双方达成一致后执行；当前不部署。未确定的价格套餐、平台费率、多人规则和最终支付产品留到相应阶段讨论。
