## 目标与范围

客户已有球友，通过微信与智能体沟通，完成空场咨询、查价、选场选时、预订占位、在线缴费、确认和查询预约。人人匹配后置。

运营工作人员也通过微信与智能体协作，完成代订、人工预约登记、课程占场、预约调整与取消、异常处理及人工接管。保留手机可用的排场后台。客户、员工、后台共享同一订单和同一份场地库存。

在线缴费属于 MVP 主链路。人工收款登记可以作为补充，但不能替代真实支付发起、结果验证和订单确认。

课程首期按“课程占场”控制范围；完整教务、招生接龙、课包、自动约教练不纳入本次基础建设。已确认首期不自动校验教练时间，不做自动循环排课。

2026-09-18 补充确认：同一预订人可以同时预订同一时段的多片球场，属于 MVP 必须支持的情形。撤回此前“一笔预约限定一片场地”及“多场地组合订单不在范围”的假设。预订人的时间重叠不能作为场地冲突依据。

采用“一笔预订包含一条或多条场地明细”的设计，每条明细分别记录一片球场和自己的起止时间；同一笔预订可以包含不同时间的明细。计价按明细计算后汇总。一次预订三片球场不应迫使客户重复三次对话。已确认同一场馆内一单多明细、整组占位全成或全败、整单支付，授权员工可以按明细部分取消或改期；现有 F0 仅完成单片占用基础，尚未实现多明细原子占位或完整订单。多人分账仍不纳入当前基础建设。

## SaaS 运营与多租户：已确认

我方为 SaaS 运营方，服务多个独立租户。MVP 按多租户架构建设，试点计划先开通格林一个真实租户，并用第二个合成测试租户验证隔离；由我方人工开通租户并人工收取软件服务费。此处是已确认的运营方案，不表示真实租户或第二测试租户已经创建。

- 平台负责创建租户、设置服务状态和初始租户管理员；自助注册、套餐订阅、自动续费及分销后置。
- 租户是独立客户与数据管理边界，可拥有多个场馆。校区不是天然独立租户；独立签约及管理的经营方另行确定归属。
- 业务层级为“我方平台 → 租户 → 场馆（校区）→ 单片球场”。格林为首个计划试点租户。
- 场馆、球场、价格、客户业务档案、库存、预订、支付及会员数据须归属租户。后台、微信、Agent、回调和定时任务均校验租户上下文，禁止跨租户访问与关联。
- 平台运维管理与租户业务管理分开；平台协助处理业务使用明确授权和审计记录。
- 租户收取场地订单款与我方向租户收取软件服务费分开。SaaS 运营方式不代表我方统一代收场地款；商户接入方式仍需确定。
- F1 已补内部租户/场馆/球场归属、员工权限及带租户的库存事务，两个合成租户隔离已验证；公开认证、租户管理后台及完整业务隔离仍待接入，不等于完整多租户 SaaS 已验收。

## 租户后台：场地资产、价格与分时折扣

这些功能纳入 MVP，由租户内有权限的管理员自行维护自己租户的数据，不要求每次通过平台运营方或开发者改配置。

| 能力 | MVP 范围 |
| --- | --- |
| 场馆资料 | 校区／场馆名称、地址、营业时间等基础资料 |
| 球场资产 | 球场编号／名称、所属场馆、室内外等必要属性、启停状态 |
| 可用性维护 | 营业时段、维护与临时关闭；变更时提示受影响的已有效预约，不能静默覆盖 |
| 基础价格 | 设置各球场的标准小时单价；小时价格与最小 15 分钟调度粒度分开 |
| 分时折扣 | 选择适用场馆内的球场、适用日期／星期、使用起止时段、折扣及生效日期范围 |
| 配置留痕 | 记录配置版本、操作人、生效时间；报价与订单保留其使用的价格依据 |

分时折扣按实际使用球场的时段匹配。例如同一片场标准价 100 元／小时，工作日 10:00–18:00 打 8 折、18:00–22:00 原价；17:30–18:30 应拆为两段，金额为 0.5 × 80 + 0.5 × 100 = 90 元。示例金额用于说明算法，不是格林真实价目。

一笔预订有多条场地明细时，先对每条明细按价格／折扣边界分段计算，再汇总到预订单。时间边界遵守 15 分钟粒度，星期和时段按场馆当地时间判断，常用选时仍为 1 小时。计价由 PMS 确定性服务完成，Agent 解释报价结果。

用户已确认 MVP 折扣策略：同一球场、同一使用时间最多命中一条有效时段折扣，未命中时使用基础价；重叠配置在保存／发布时提示解决，未解决不得生效，不自动相乘或猜测优先级。会员余额按人民币消费金额管理，会员身份不增加额外折扣；优惠券首期后置，特殊日期按无重叠价格规则表达，不自动选择优先级。

更新价格规则不得追溯改写已确认订单；有效报价的价格版本与有效期应按约定锁定，过期或变更需求后重新报价并确认。金额使用整数分，分段分摊与最终舍入方式在计价实施规格中固定并验证。价格配置权限需区别于普通接单权限。

实施状态：租户后台、资产目录管理、网球定价引擎和分时折扣均待开发；本次确定产品范围，不将住房原价目或已有构建当作这些能力已经完成。

## 会员人民币余额：已确认

用户最新明确：会员按人民币消费余额管理，例如充值 10,000 元、获 12,000 元可消费金额；先按场地实际价格和时段折扣形成应付金额，再从余额扣除相同金额，不因会员身份再打折。示例不固定各租户充值档位，会议历史中的会员价不同时继承。

会员储值余额与消费明细纳入本期，支持客户查询本人、员工按权限办理和核对。实际收取的本金与赠送消费额度分别留痕，金额用整数分，充值、消费、退款均有来源和幂等流水；住房房晚权益不能改名当人民币。已确认同租户跨校区通用；按充值先后及每笔本金/赠送比例扣款，订单退款恢复原构成；允许余额＋微信补差，禁止透支。支持线上充值和授权员工登记真实线下收款，退卡提现/转赠/余额过期后置。完整规则见 [开发决策与验收清单](decisions-and-acceptance.md)。

充值预收、赠送、消费扣款和已完成服务分别记录，不能合并当作营收。当前尚无人民币钱包或网球支付实现；这是已确认需求，不是账务功能完成声明。

## GreenPMS 体验延续：已确认

在满足网球业务的前提下，尽量保留 GreenPMS v1.4.3 的视觉效果、信息密度、导航与操作习惯；**后台 AI 助手必须保留**，不能因精简 MVP 而删除。延续原有深绿主色、浅灰绿背景、表单/弹窗/状态组件、桌面侧栏与手机底部导航。房态改为排场、按天改为 15 分钟调度等必要变化围绕业务展开，不另换设计体系。

后台 AI 助手和微信 Agent 是两个使用入口，共用受权限约束的 PMS 业务能力；保留原助手的页面/订单上下文、查询与入口引导、常用提问及反馈。原助手不是自动交易实现；网球写操作仍须遵守确认、权限、幂等和回执规则。用户明确 AI 配置由我方平台统一管理，使用指定模型与 Base URL，租户不配置。智能体与 Runtime 位于 PMS 外部，本次只保留助手面板和外部服务适配、受控业务 API，不在 PMS 内新建 Runtime。

将排场就地办理、返回位置与筛选保留、条件允许时不丢表单输入、提交结果恢复、费用与变更摘要、客户资料预填、今日任务、手机与键盘可用性作为对应 MVP 切片的质量要求。界面记忆、草稿和 AI 上下文须按身份/租户/场馆隔离，不能为保留操作习惯降低权限控制。

具体继承依据与验收目标见 [GreenPMS 体验延续清单](experience-continuity.md)。当前 fork 保留原 UI/AI 源码，但网球业务与多租户适配尚未完成；本次是规格确认，不是新版界面验收。

## 时间规格与预订组合

2026-09-18 最新修正：最小时间粒度为 **15 分钟**，**1 小时为常用预订时长**。此前“常用 30 分钟”的表述被本次决定替代。15 分钟是调度粒度；常用 1 小时不等于只允许订 1 小时，也不自动成为最短可售时长。

- 起止时间按场馆当地时间对齐至每小时的 00、15、30、45 分，时长为正的 15 分钟整数倍。15、30、45、60、90、120 分钟都能被数据模型表达；具体可售时长与营业规则另行配置。
- 常用交互默认选一片场地和 1 小时，可以调整时长、增加同段场地；较特殊的不同时间明细按需展开，不强迫日常单片预订使用复杂表单。
- 每条明细持有自己的 courtId、startAt、endAt；订单上的汇总时间不能替代这些明细时间。

| 情形 | 同一场馆内的示例 | 表达方式 |
| --- | --- | --- |
| 常见：一人订一片、一个时段 | 1 号场 19:00–20:00 | 一笔预订、一条明细 |
| 一人订同一时段多片 | 1、2、3 号场均为 19:00–20:00 | 一笔预订、三条明细 |
| 特殊：一人订不同时段 | 1 号场 18:00–19:00；2 号场 20:00–21:00 | 一笔预订、两条明细，各自持有时间 |

同一片球场也可以有两条不连续明细，例如 1 号场 18:00–19:00 与 20:00–21:00，中间 19:00–20:00 仍为空闲，不能按订单的最早开始至最晚结束把间隙占掉。同人不同片即使时段重叠也不构成场地冲突；同片明细之间仍须检查重叠。一笔订单限同一场馆，授权员工可按明细部分改退；资金按原来源分摊与退回，不允许累计多退。

实施状态：各条占用有独立时间；F1 已在领域与数据库追加 15 分钟对齐约束，拒绝非边界时间而不取整。完整预订单及多明细整组事务仍待实施，单条库存通过不等于组合预订已完成。

## 组件边界

| 组件 | 责任 | 不应承担的决定 |
| --- | --- | --- |
| 微信 Gateway | 消息接收与回复、渠道身份验证、消息去重 | 库存判断、付款认定 |
| Agent 与人工协作 | 理解需求、补齐参数、调用受控工具、确认意图、保存业务上下文、人工接管 | 绕过权限直接写数据库、用聊天内容认定到账 |
| PMS 业务核心 | 场地、营业规则、时段库存、价格与报价、订单、支付/退款状态、权限、审计 | 替代渠道返回真实支付结果 |
| 平台管理后台 | 人工开通租户、初始管理员、服务状态与授权支持记录 | 默认取得无限租户业务权限 |
| 租户运营 Web 后台 | 场馆／球场维护、价格与分时折扣设置、排场、接单与异常处理、内置 AI 助手；延续 GreenPMS 体验 | 独立维护第二套订单或库存、跨租户操作 |
| 支付适配 | 发起支付/退款、验证结果、主动查单与补偿 | 由模型猜测支付是否成功 |

微信 Gateway 具体产品由外部智能体侧确定；智能体及 Runtime 在 PMS 体外，本次不开发其运行时。PMS 提供受控 API、事件、人工接管和后台助手适配。PMS 是整个网球项目的组件。MVP 沿用模块化单体，不要求一个组件一个仓库或一个进程。

## 资产称谓与层级：已确认

2026-09-18 用户确认：“校区”和“网球场／场馆”是同一经营地点的不同称呼，属于同一层；一个场馆下包含多片球场。不能建立“校区 → 场馆”的额外父子关系或重复库存。

```text
我方 SaaS 平台
├─ 格林网球（Tenant）
│  ├─ 省体校区／省体网球场（同一个 Venue）
│  │  ├─ 1 号场（Court）
│  │  └─ 其他独立球场
│  └─ 其他校区／网球场（另一个 Venue）
│     └─ 各片独立球场（Court）
└─ 另一经营机构（另一个 Tenant）
   └─ 其场馆与球场
```

- 场馆（Venue）：具体经营地点，承载地址、营业规则及管理范围。校区是同层业务别名，不是新增资产层级。
- 一片球场（Court）：可独立分配、按时间占用的物理资源，具有独立 ID 和场地编号，隶属一个 Venue。不同场馆可以都有“1 号场”，系统必须通过场馆与具体资源 ID 区分。
- 库存粒度为“一片球场 × 时间区间”；预订人、场馆整体或整个订单不代替单片资源进行冲突判断。
- 一个预订人可关联多笔预订；一笔预订关联多条场地明细，每条明细关联具体 Court 和时间区间。客户订三片场不产生三份重复客户档案。
- F1 已有正式租户/场馆实体、球场复合归属外键及员工场馆范围；资产维护后台、公开认证和账务仍未完成。

## 核心业务约束

1. 一条场地占用采用 `courtId + [startAt, endAt)`，业务最小粒度为 15 分钟，常用预订时长为 1 小时。同一片球场的相邻时段可共存、重叠时段互斥；不同球场可被同一预订人在同一时段预订，45 分钟课程也能准确占用。
2. 租场、课程、维护进入同一库存并遵守 15 分钟调度粒度。营业时间、各产品最短可售时长和缓冲时间另行校验，不从常用 1 小时推导销售限制。
3. 查询到空闲不代表已经占位。写入时再次校验；数据库约束保证并发请求不能重复占同一场地。
4. 报价有效期与待付款占位期限分开。预订状态、资金状态分开；付款成功以服务端校验的支付结果为准。
5. 库存冲突或改期失败保留原预约。取消预约、释放库存和退款各自有明确结果，不用一次状态修改冒充所有动作完成。
6. 客户只操作本人订单，员工按权限代办。记录预订人、操作人、付款人及服务执行主体。员工接管后按自己的身份重新预览和确认。
7. 写入应具有幂等、事务复核、审计和可恢复回执；重复消息不重复交易。
8. 人工接管阻止旧 Agent 任务继续改同一业务；支付回调、到期释放等确定性业务任务继续执行。
9. 多片请求需满足约定数量和时间，例如“三片、19:00–21:00”要求三片都在整个时段可用，不能用不同时段轮换拼出数量。若只能提供两片，应明确告知，不得把部分结果说成全部预订成功。已确认同次确认的整组占位在一个事务内全部成功或全部回滚，待订单切片落实。

10. 租户资产与价格配置、客户/员工/Agent 业务操作，以及异步任务均须验证租户归属。用第二个测试租户覆盖越权查询、改写和跨租户业务引用，不能只依靠前端筛选。
11. 场地价格和时段折扣按各租户配置计算；跨价段拆分，多明细汇总，保存价格版本和明细依据。修改配置不追溯改变已确认订单。

## 已确认规则与实际接入限制

| 事项 | 规则与当前条件 |
| --- | --- |
| 订单 | 一单限同场馆、多明细；整组占位全成或全败、整单付款，授权员工可按明细部分改退 |
| 报价与占位 | 默认报价有效 5 分钟；确认后待支付占位 10 分钟；租户管理员可配置，两种期限与 15 分钟调度粒度无关。已有报价/订单保留原期限，到期释放 |
| 退改及特殊情况 | 客户申请，授权员工确认金额与理由后执行，退款退原来源；雨天、停场、迟到和爽约由人工处理，AI 不决定费用 |
| 未付款预约 | 仅授权人员可保留，必须填写付款截止时间和原因；不能标记为已收款 |
| 储值与混合支付 | 同租户各场馆通用，按充值顺序及本金/赠送比例扣款、退款恢复原构成；允许余额＋微信补差，禁止透支 |
| 会员扩展与优惠券 | 退卡提现、转赠、余额过期、优惠券均后置；会员不另打折 |
| 课程与财务 | 课程仅占场，不校验教练冲突、不自动循环排课；提供基础流水核对，不做完整财务/教务 |
| 可售时长 | 调度 15 分钟、常用 1 小时；最短可售时长由租户明确配置，不预填格林真实营业或售卖规则 |
| AI | 平台统一配置指定模型/Base URL；外部智能体和 Runtime 不在本次开发范围，助手 UI、受控接口与适配保留 |
| 支付商户 | 暂无商户号，场地款与充值款直接进入租户商户；本地模拟验证，实际支付与退款待商户接入 |
| 部署及期初 | 暂无测试服务器、域名及价目；本地模拟数据开发，上线前核对导入真实资产、价目、有效占用和会员期初 |

## 实施顺序与完成口径

1. 独立本地数据库、端口和迁移；停用继承的住房启动/重置及生产发布入口。验证区间库存和真实数据库并发防重。

3. 按已确认占位/退改和钱包规则完成报价、预订、人民币余额与混合支付、授权/审计及支付适配；真实商户条件具备后联调。
4. 沿用 GreenPMS 视觉和操作习惯建设手机可用的排场后台，并适配内置 AI 助手；提供客户与员工外部微信 Agent 的受控接口、助手适配及人工接管。各业务切片同步验收体验清单。
5. 导入试点全部有效占用，分别验收客户自助、员工代订、人工接管与真实支付。

基础库存测试通过只证明库存技术切片完成，不代表预订接口、运营后台、微信或支付闭环已完成。
