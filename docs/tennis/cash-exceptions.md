# 异常实收的原路退款（F10）

状态：本地实现与自动/浏览器模拟验证完成；真实渠道和客户人工验收待完成。来源是已确认的迟到/重复实收核对及原路退款要求，不新增退卡提现、任意调余额或自动退费政策。

## 触发与处理

下列款项已经由支付适配器验证为真实渠道事实（本地演示为明确 MOCK），但没有用于成交或增加可消费余额：

- 预约到期、取消，或改期已失效后收到的外部付款。
- 同一订单付款记录收到第二笔不同交易号的实收。
- 同一充值单收到第二笔不同交易号的实收；不会重复增加本金或赠送。

员工从“资金核对 → 实收待核对”打开原异常，核对来源、金额、原渠道交易号，填写原因，明确申请把这笔未使用的外部实收全额退回原渠道。金额以渠道已验签交易登记为准，不能直接信任列表备注或请求中的数字；提交金额须与原额一致。

原异常记录保持 OPEN，直到取得已验证的退款成功结果才变为 RESOLVED。发起、处理中、未知、失败都不能直接关闭异常。每条异常只有一条内部退款申请；重试不重新分配资金，不允许通过换幂等键重复退款。

## 不变量

- 仅处理未用于成交的对应实收交易号。已用于订单或已正常入账的钱包充值不能通过伪造异常绕过常规退款/退卡边界。
- 不改变订单明细、场地库存、会员本金或赠送余额；迟到付款不会恢复已经释放的场地。
- 退款固定原租户、客户、原交易号、原商户版本及金额。平台后续换商户不改变这笔退款的去向。
- 员工查看异常需要 manage_members；申请/重试还需要该场馆的 refund 权限。客户不能决定退款金额或发起异常退款。
- 异常退款与普通订单退款共同防止复用同一个渠道退款号。已成功后的晚失败不能回滚，重复成功不能再计一次现金退款。
- 结果未知时查询原操作；只有明确终态失败且授权员工重试，才产生新渠道代次。沿用 F9 已验证的持久投递、通知归属和恢复规则。
- 退款成功事实与异常关闭、审计、事件同事务完成。财务核对新增现金负向流水，会员余额列为零，不能把异常款退款当作再次恢复会员消费额度。

## 接口与界面

- GET `/cash-exceptions/:id`：员工核对原实收和当前退款申请。
- POST `/cash-exceptions/:id/refund`：`amountCents`、`reason`、`commandKey`；金额固定原额。
- GET `/exception-refunds/:id`：读取当前退款状态，客户只能读本人退款。
- POST `/exception-refunds/:id/retry`：授权员工对明确失败退款重试。
- `/exception-refunds/:id/channel`、`/channel/reconcile`：读取渠道快照、恢复原结果。
- `/exception-refunds/:id/simulate`：仅本地 MOCK 验证，不发生真实退款。

以上省略 `/api/tennis` 前缀。新接口继续要求会话、租户与动作权限、CSRF、工作区版本。没有“手工标记已退款”接口。

## 验收

三类异常须各自覆盖：原实收核验、并发/幂等、跨租户及场馆权限、原商户退款、未知恢复、失败重试、成功关闭、现金台账和业务事件。特别核对重复充值退款不改原钱包批次，迟到付款退款不改变他人已经预订的场地。

真实渠道、商户联调与客户人工验收仍待外部条件。最终实施和验证结果见 `implementation-status.md`，本文不作为已完成声明。
