## 结论与范围

当前 PMS 已有“后台助手调用外部服务，再授予本次工具调用权限”的适配。它不等于“微信 Gateway 可以独立完成身份绑定、消息接入、异步结果接收和人工协作”的完整接入。

智能体及 Runtime 保持在 PMS 体外。下一切片只补 PMS 的身份与授权边界、受控接口、结果关联和接入契约，不实现模型规划、记忆或自主循环。微信具体产品、实际账号、商户、服务地址与部署条件尚未确定；本文件不选择微信产品、不创建客户账号，也不改变已确认资金规则。

- [MVP 与组件边界](mvp.md)：客户/员工微信入口、PMS 受控 API 与事件、支付适配和人工接管。
- [开发决策与验收清单](decisions-and-acceptance.md)：同租户替代场馆查询、可信客户绑定、租户分别收款和外部条件边界。

## 无需外部账号即可补齐的内容

### 1. 同租户替代场馆发现与查询

**规格要求：** 于娜访谈中的“省体无场推荐另一校区”已收敛为同租户授权范围内查询替代场馆，须明确场馆和完整所需时段。

**当前缺口：** Agent 工具没有场馆发现或替代场馆查询入口；排场和报价均取临时凭据绑定场馆，授权检查拒绝其他场馆。后台能切换场馆，不代表一次外部咨询能完成替代推荐。

**最小技术建议，尚未实施：**

- 增加只读发现能力，例如 `GET /agent/venues` 与按目标起止时间、所需球场数量查询的替代场馆接口。
- 限于当前租户；客户只能发现可售场馆，员工还须符合本人场馆权限。结果给出场馆 ID、名称、地址、时区、可满足的完整时间范围及球场，不泄露他人预订身份。
- 推荐不锁场，不改变当前会话的写权限。客户选定另一场馆后，通过受控流程取得该场馆的新交易作用域，重新报价和确认。
- 保持一单一场馆；不新增跨租户推荐、跨场馆合单或多人分账。

**本地验收建议：** 当前场馆无场、同租户另一场馆可满足；整组多片需求不能用零散空档冒充满足；无权场馆和其他租户不进入结果；旧写授权不能用于新场馆下单。

### 2. Gateway 身份、绑定和入站会话契约

**规格要求：** Gateway 验证渠道身份，PMS 基于可信主体执行客户/员工权限；客户报出手机号不产生余额扣款权限。

**当前缺口：** HTTP 边界主要接受本地登录 cookie 或 PMS 签发的临时工具 token。当前 token 在后台助手派发时产生，没有“受信 Gateway 来信 → 已绑定主体 → 会话/工具授权”的独立契约。客户主体绑定目前存在于本地账户与客户档案中，不能直接当成微信绑定。

**最小技术建议，尚未实施：**

- 先定义渠道无关的集成主体及租户范围、凭据验证与撤销方式；具体微信标识留作适配器输入，不在 PMS 核心假设 OpenID、企业微信外部联系人 ID 或昵称可以互换。
- 定义受验证外部主体与 PMS `subjectId`、租户内客户/员工身份的绑定记录。不得让聊天正文或普通请求自行声明 `tenantId`、权限或 `customerId` 来完成绑定。
- 定义入站消息唯一标识、去重、会话关联、身份被撤销后的处理和有限授权签发。后台助手派发与 Gateway 入站可以复用业务授权规则，但不是同一个认证入口。
- 首期可继续后台建档及人工核对绑定；不引入自动注册、按手机号自动合并客户、跨租户通用身份或共享会员余额等新规则。

**本地验收建议：** 用合成集成主体验证租户/主体不可伪造、重复来信不重复业务操作、绑定撤销生效、客户与员工权限分离。合成资料不等于真实微信账号或已完成真实首绑。

### 3. 对外业务事件契约

**规格要求：** PMS 对外提供受控 API、事件和人工接管能力。

**当前缺口：** 当前有内部审计、支付事件和命令回执，但没有面向外部组件的业务事件流、游标或可靠投递契约。内部数据库表不是外部集成 API。

**最小技术建议，尚未实施：**

- 只定义主链路需要的事实：预订确认/到期、付款和充值结果、退款结果、人工接管状态变化。事件代表已提交事实，不通过自然语言回复推导。
- 事件至少包含稳定 `eventId`、事件类型、租户/场馆范围、业务资源 ID、发生时间和协议版本；按权限提供必要字段，不默认附完整客户档案或聊天内容。
- 业务事实和待发布事件可靠关联。首期可采用受控的游标轮询，不必先做 webhook；须明确重复读取、断线续读和消费者去重。
- 事件消费权限独立于某次 30 秒助手派发的写 token，同时仍受租户/资源范围及撤销约束。
- 提供事件不等于授权实际发送微信通知；消息渠道发送仍由外部组件和真实渠道能力处理。

**本地验收建议：** 重复回调不生成重复业务事实；消费者中断后能从游标续读；跨租户、无权场馆及客户他人业务事件不可见；人工接管与业务事件顺序可解释。

### 4. 超时消息的命令关联与结果恢复

**规格要求：** 外部结果未知时先核对原订单/回执，不盲目重发可能已执行的交易。

**当前缺口：** 助手派发结束即撤销该 token；`UNCERTAIN` 消息阻止继续派发。消息派发记录与业务命令回执没有持久关联；原回执又按原操作主体查询，接管员工不能仅凭会话定位这次外部调用产生的全部命令。

**最小技术建议，尚未实施：**

- 持久关联 `conversationId/requestId → commandKey → 业务结果`，使未知消息可以核对具体命令，而非只显示笼统提示。
- 为有权接管的员工提供按会话关联查询的最小结果视图，不通过冒用客户身份读取回执，也不开放任意主体的全部回执。
- 区分只读结果恢复与恢复写授权。结果未知、接管或平台停用后，不因要查状态就延长原写 token；恢复写操作仍需新的明确授权状态。
- 明确外部适配器保存和重用原 `requestId/commandKey` 的责任；同一意图重试不能另建交易。

**本地验收建议：** 模拟命令已提交但回复丢失，接管员工能定位其结果；重复核对无副作用；新授权不能扩大原租户/场馆/客户范围；旧写 token 始终失效。

### 5. 支付适配接口与真实渠道替换点

**规格要求：** 支付适配承担发起支付/退款、结果验证、主动查单与补偿；场地款和充值款直接进入各租户商户账户。

**当前缺口：** 付款/充值业务函数直接依赖 `LocalMockPaymentGateway`，模拟器提供签名及验签，尚无统一的发起、退款、查单接口或交给入口展示的付款动作契约。真实渠道接入仍需要代码，不是仅填写配置。

**最小技术建议，尚未实施：**

- 固化与具体微信产品无关的支付端口：创建付款、查询付款、创建退款、查询退款、验证通知；输入包含稳定业务请求标识及已受控解析的租户商户绑定。
- 明确发起成功、明确失败和结果未知的区别，以及查询/重试时保持原付款或退款标识的要求。
- 定义供入口消费的付款动作结果；具体渠道参数由适配器负责，模型不能编造二维码、支付链接或认定到账。
- 保留现有金额、原路退款、余额预留和防透支规则；模拟适配器用于契约验证。不得将 MOCK 事件包装成真实渠道事实。

**本地验收建议：** 模拟发起后丢响应、主动查到成功、同请求重试不重复发起、错误租户商户拒绝、退款保持原支付来源。真实 SDK 参数、商户证书和真实资金验证不在这些本地测试中冒充完成。
