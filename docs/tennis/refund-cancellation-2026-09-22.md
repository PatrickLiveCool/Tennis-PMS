# 退款与取消时段的操作意图修复

## 问题与事实

本地演示订单 `2aa0e7f1` 包含“演示球友”2026-09-22 18:00–19:00 的一号场、二号场。原操作仅为一号场退回 120 元，退款成功但 `cancel_line=false`，两条明细均未取消、占用均未释放。原表单默认不取消，却固定显示“确认退款与取消明细”，完成提示又只说明退款到账，容易使工作人员误认为已经释放场地。

后端契约允许仅退款保留预订，不能以付款状态推断库存。取消时段在退款申请事务中同步写入取消和释放记录；排场只读取有效占用，原刷新链路有效。本轮保持这些规则。

## 修复行为

- 新草稿选中时段后，必须明确选择取消并退款或仅退款保留预订。旧布尔草稿保持原意，不静默取消已有预订。
- 提交前列出将释放、保留及此前已取消的具体时段；按钮随实际处理方式和金额变化。成功提示同时说明资金状态与本次库存结果，来自提交前的请求快照，不受表单重置影响。
- 全单或部分明细已退清但仍有效时，支持零元补取消。此前已取消行的后续退款不再请求重复取消；仅退款零元、金额超额和未选择处理方式均在提交前给出错误或阻止提交。

## 本地演示修正

通过 `demo.staff` 登录本地模拟 API，核对原退款、明细和订单版本后，按用户取消意图，仅为一号场执行 `refundCents=0, cancel=true`。保留原 120 元退款，二号场明细及有效占用保持原状。API 回读验证一号场已取消、排场仅剩二号场；浏览器也确认一号场预订块消失且二号场仍显示已预订。

修正脚本及前后快照位于本地忽略目录 `.local-workspace/refund-inventory-repair-20260922.mjs`、`.local-workspace/refund-inventory-20260922/`。没有直接 SQL 改库存、没有真实商户资金动作或生产变更。
