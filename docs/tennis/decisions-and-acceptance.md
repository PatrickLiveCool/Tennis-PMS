## 人民币会员余额：最新已确认

1. 会员用人民币消费金额管理。示例充值 10,000 元、可消费 12,000 元，可表达为实收本金 10,000 元加赠送消费额度 2,000 元；示例不是所有租户固定充值档位。
2. 先按球场价格及时段折扣形成订单应付金额，再按相同金额扣会员余额。会员身份不新增折扣层，也不改变原价目。
3. 例如订单应付 90 元，可消费余额从 12,000 变为 11,910 元；这不表示应从银行卡再扣 90 元，也不表示 2,000 元赠送额是实收现金。
4. 需保留充值来源、实收/赠送区别、消费与退款流水和可核对的余额，使用整数分与幂等事务；不能把住房房晚权益改名当人民币。支付事实由受控服务验证，客户身份由可信绑定核验，不能仅凭报出手机号扣款。
5. 用户确认：同租户跨校区通用，按充值先后及每笔本金/赠送比例扣款，退款恢复原构成；支持余额＋微信补差、禁止透支；退卡提现、转赠和余额过期暂不做。充值支持线上支付及授权员工登记真实线下收款。

充值实收、赠送额度、订单收款、储值消费与服务完成分别保留事实，不能相加当作收入，更不能把预收充值直接认定为已实现营收。首期拟做基础台账核对，完整财务系统不纳入本期。

| 阶段 | 实施及验证 |
| --- | --- |
| F0 既有基础 | 独立环境、单片整分钟区间库存及数据库冲突约束已有验证；不是完整预订 |
| F1 已定基础 | 15 分钟约束、租户/场馆/球场归属与权限、跨租户否定用例；这些不依赖钱包扣款政策 |
| F2 配置及交易 | 资产/价目/折扣后台，报价、多明细预订与到期释放；按已确认规则处理资金和整组事务 |
| F3 余额与支付 | 独立人民币账本、充值/消费/退款/查询，余额＋微信补差、支付渠道校验、重复回调、并发扣款与到期竞争；真实资料导入有来源与核对 |
| F4 工作流与入口 | 复用 GreenPMS 体验，排场/订单/客户/工作台/设置/后台助手，为外部微信智能体提供客户/员工受控 API、事件、人工接管及助手服务接口；不开发外部 Runtime |
| F5 综合验收 | 两租户隔离；一片/同段多片/不同时间明细；跨价段报价；储值和微信支付；员工代办、接管和退改；断网恢复；实际渠道与商户证据 |

不因本地或模拟测试通过而声称真实微信/商户已联调，不因自动测试通过而声称客户人工验收通过。缺少外部条件时继续完成独立开发、集成适配、模拟测试和可运行演示；对应真实验证项保持未完成。goal 持续追踪这些差异，不提前标为完成。

## 支付与外部智能体的执行边界

混合支付必须记录余额部分与微信部分。待微信补差期间，预留相应会员可用额度并占位；未成功前不能将整单写成已付。失败或到期可恢复可用余额，迟到支付通过确定性异常流程处理，不能重新抢占他人已订场地。退款按原资金来源及原本金/赠送构成退回，不把赠送额变成现金。精确到分的分摊与累计退款上限在实施规格固定并测试。

后台助手面板保留，PMS 提供受控查询/操作入口和外部助手服务适配；不在 PMS 内新建模型规划、记忆或自主循环 Runtime。指定模型/Base URL 仅由平台运营角色管理，密钥不向租户暴露。外部 Runtime 的具体协议可由适配层接入，未连接时明确显示状态，不用模拟回复冒充真实 AI。
